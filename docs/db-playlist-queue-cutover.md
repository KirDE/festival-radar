# DB playlist queue cutover barrier (issue #210)

The queue claim is dormant. It serializes simultaneous **queue callers** per festival using a transaction-scoped PostgreSQL advisory try-lock plus a fresh-snapshot RUNNING-sibling check. A different festival can be selected while a festival lock is held. This is not permission to start a production worker.

Each `claimPlaylistRefresh` call checks at most 16 distinct festivals and returns `{ claim, nextCursor }`. A future worker must pass a non-null `nextCursor` to the next call when no claim was made; a null cursor means the scan is exhausted, and the next poll starts at the beginning. After a successful claim, start a new scan. The cursor is a scan position, not a durable job acknowledgement; do not treat a page without a claim as an empty queue.

Before enabling it, stop and drain the existing `/api/playlists/run` route and its collection script/scheduler. That route does not use the DB lease: it marks batches RUNNING via `updateMany`, then executes Spotify effects, and its success/failure updates are not owner/attempt-fenced. A DB claimant and that route can overlap, and the route can overwrite a newer owner's state. Do not switch only the scheduler or turn on both consumers. Fence Spotify calls and catalog upserts in the new worker, with a lease check immediately before every external write (and a policy for calls already in flight); ensure no legacy invocation remains active before cutover.

Inspect production queue rows read-only, grouped by festival and status, especially `RUNNING` without `leaseOwner/leaseExpiresAt` and `FAILED` without `retryAt`. A legacy unleased RUNNING row blocks its festival, even if old `startedAt` has passed. A legacy FAILED row with null retryAt is dormant. Reconcile each row only after verifying the old process has ended and Spotify/catalog read-back is known. Record the decision per publication; do not bulk reset RUNNING/FAILED or infer success from timestamps. This change does not modify production rows.

Lease expiry allows an attempt-fenced *database claim* to be reclaimed, but does not cancel an already in-flight Spotify call. Until the worker has side-effect fencing and an explicit expiry/renewal policy, lease reclaim is **not** end-to-end exactly-once execution. Advisory locks are cooperative: all claim paths, including any future manual API, must use this protocol. Completion's attempts/owner/expiry check only fences DB acknowledgement, not Spotify or legacy route writes.

Dormant DB fencing prerequisite: `assertPlaylistRefreshLease` validates the original job/publication/festival/owner/attempt against database time, after acquiring the shared festival advisory lock and job row lock. A caller-supplied expiry is not authoritative. Any RUNNING sibling, including an unleased legacy row, rejects ownership. Use this check immediately before each future Spotify write; ownership can still be lost after the check returns.

`commitPlaylistRefresh(db, claim, write)` runs a trusted DB-only callback under those same locks, supplies the publication's festival and edition year, rechecks DB-time expiry after writes, then commits SUCCEEDED and catalog writes together. Use only the supplied transaction client and scope for that publication's playlist upserts; do not invoke external services, mutate queue rows, or write unrelated festivals in the callback. An exception or lease loss rolls back the entire transaction. Reclaims cannot overlap the transaction; a lease that expires during the callback cannot commit. `finishPlaylistRefresh` uses the same identity/serialization/DB-time fence; its existing caller clock may tighten expiry but cannot bypass DB expiry. Neither API resurrects legacy unleased RUNNING jobs. No schema migration or live consumer is added.

Remaining activation blockers: bounded renewal with a fixed maximum attempt lifetime is not implemented; the existing claim still accepts caller time, so a worker needs a DB-time claim/renewal policy before activation. Keep catalog transactions short and retry expired work only through a fresh claim. Stop/drain the legacy route and reconcile its rows first. A Spotify request in flight after lease loss cannot be revoked: DB fencing does **not** make Spotify calls exactly-once. Before enabling a worker, implement pre-call ownership checks plus Spotify read-back, idempotency and reconciliation for ambiguous/in-flight results; preserve the fallback until cutover is separately reviewed.
