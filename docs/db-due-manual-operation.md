# DB due worker: manual-only foundation (#210)

This adds an **operator-triggered, fixed-mode systemd unit**, not a timer, recurring workflow, or scheduler switch. Deployment still enables the existing ingestion/notification timers; do not run this in production merely because the unit exists.

After a reviewed release is packaged, deployed and verified, an operator can inspect the installed unit and wrapper and explicitly start a single operation with the exact 40-character currently deployed release commit:

    sudo /usr/local/libexec/festival-radar/start-db-due <deployed-commit> health
    sudo /usr/local/libexec/festival-radar/start-db-due <deployed-commit> ingest
    sudo /usr/local/libexec/festival-radar/start-db-due <deployed-commit> drain

Direct use of `start-db-due` requires an existing privileged operator; no sudoers grant for that wrapper is installed. The already-granted root-owned `activate-release COMMIT` entrypoint accepts `due-health` and, after the separately reviewed pilot release, exactly `due-ingest-pilot` for the constrained deploy user, never unrestricted ingest or drain. It validates the mode, current symlink, release marker and deployment lock; the unit runs as www-data from the pinned release. **This wrapper is not a security boundary against the application user:** www-data owns the release and has the application DB credentials, so it can invoke the DB operations without the wrapper. This change provides an operator workflow and serialization with deployment, not database privilege isolation. Achieving that requires a separate DB role/ownership redesign. If release health fails, deployment restores the previous unit and wrapper (or removes them if absent), reloads systemd, and restores the previous release. Ingest processes at most one due source, drains at most 100 staged events on a separate invocation, and discards private worker artifacts after completion. The health invocation writes a fresh private root-owned audit file under `/run/festival-radar-db-due`, removed after completion; only an exact validated numeric record is forwarded to the operator: due, due >1h, active leases, expired leases, enabled sources with failures, pending outbox events, events pending >1h, and unknown parser-key rows. No source strings, event payloads, error text or secrets should be printed. Unexpected errors are suppressed to fixed status messages (or exit codes).

For disposable PostgreSQL verification only, set a test/integration DATABASE_URL and run `npm run test:due-worker` (includes DB health E2E); never point it at production.

**Activation gate:** verify a deployed SHA, migrations and configuration backfill, take count-only health before and after a manual test, inspect lease recovery and outbox drain counts, and compare catalog/notifications with the legacy ingestion path. Keep the old scheduler active for now; do not run overlapping source fetches during a manual pilot. Only a separate reviewed change should switch the scheduler after idempotence and operational monitoring are proven. There is no automatic start and no production source operation in this change.

## Protected GitHub Actions read-only pilot

After review, merge and normal deployment, an authorized operator may manually dispatch **DB due read-only health** from **main**. Confirm that the live release SHA exactly matches the dispatch SHA. The job uses the `production` environment for existing SSH secrets and deploy-user sudo grant, and the deployment concurrency group. It has no mode, slug or command inputs. It invokes only `activate-release "$GITHUB_SHA" due-health`; the installed wrapper rechecks the live release symlink and marker under the deployment lock, starts only the health unit and prints a validated `DB_DUE_HEALTH` record of eight integer counts. A mismatch, missing unit/runtime, busy lock, invalid audit or worker failure fails with a fixed status message, not raw systemd/database output. Do not interpret failure as zero counts.

Before the first dispatch, verify production environment secret scope, exact main/deployed SHA, installed root-owned `activate-release` and `start-db-due` assets and unit, and the deploy-user sudo grant for `activate-release COMMIT ...`. That grant does **not** cover `sudo start-db-due` directly; do not broaden sudo or send a shell command via SSH. If an asset or grant is absent, stop and repair through the reviewed normal deployment/provisioning path. No ingest, drain or scheduler change occurs in this workflow; later pilots require separate review and authorization.

## Fixed single-source DB due pilot

After this separate change passes review, exact-head CI, merge, exact-SHA deployment and independent health, dispatch **DB due single-source pilot** on main only. It has no mode, slug, shell or scheduler inputs. The deploy-user entrypoint accepts only the exact `$GITHUB_SHA` and the fixed `due-ingest-pilot` mode. The root wrapper holds the deployment lock and a shared source-fetch lock, requires the legacy `festival-radar-collection@ingestion.service` to be inactive, runs fresh count-only DB due health under that lock, and refuses due=0 or any active/expired lease, enabled-source error or unknown parser key. The legacy HTTP ingestion endpoint (used by both its 03:23 UTC systemd timer with up to five minutes of randomized delay and the separate GitHub ingestion workflow) holds that same source-fetch lock throughout its runner process; an attempt during the pilot fails instead of overlapping a fetch. The DB due runner claims at most one due DB source, never accepts a slug/force override, and does not drain notifications or invoke a Spotify/playlist refresh executable. It can stage the existing DB playlist refresh request as part of normal publication.

The wrapper prints a validated read-only `DB_DUE_PREFLIGHT` count snapshot before claiming any source; the workflow retains it alongside the post-pilot `DB_DUE_HEALTH` counts. This is audit evidence, **not a recoverable database backup**: the documented encrypted daily backup policy and restore test still require independent operational verification before treating them as a recovery guarantee. There is no verified direct production DB route from the local controller host (no configured SSH alias, psql or .pgpass); use the existing constrained GitHub SSH-secret scope, not an invented direct DB command. Only a validated completed one-attempt `DB_DUE_PILOT` record is forwarded for the mutation outcome: `attempted`, `processed`, `published`, `reviewRequired` and `fetchErrors`. No due source is an error, not a zero-success pilot. The workflow invokes read-only count-only health again after the attempt for comparison; it does not switch or stop the legacy timer. Do not dispatch near the timer window if avoidable, and do not infer the pilot succeeded from an Actions job unless the exact release SHA, `DB_DUE_PILOT` record and post-health counts agree. Direct privileged/manual invocation outside the legacy HTTP route is not a security boundary; keep it excluded operationally. Private artifact contents are removed after the unit returns, and systemd/database errors are never forwarded to Actions.
